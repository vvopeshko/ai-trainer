# AI_TRAINER_PLAN — слой «AI-тренер»

Roadmap превращения трекера в тренера: проактивная коммуникация, чат с контекстом, инсайты, напоминания.

**Горизонт:** до состояния «тренер ощущается» (этап «для себя»). Персона тренера, голосовой ввод, видеоанализ — за горизонтом, в [PRODUCT_PLAN.md](PRODUCT_PLAN.md).

**Создан:** 2026-06-12. Основа: BRD §5.6, USER_SCENARIOS 2.4/2.6/3.2/3.3, [Позиционирование](marketing/Позиционирование_AI-ассистент_зал.md).

---

## Зачем (одним абзацем)

Дифференциатор продукта — не учёт, а **ведение**: тренер знает контекст, реагирует на каждую тренировку, замечает паттерны, не даёт бросить. Сейчас реализован трекер (домены 2–4, 6 почти ✅), а домены 7 (AI-чат) и 8 (вовлечение) — ~0%. Summary-экран уже обещает юзеру «сводка придёт от тренера в чат» — обещание надо выполнить в первую очередь.

**Целевая петля:** тренировка → мгновенная сводка от тренера → вопросы в чате в любой момент (про программу, упражнение, свою аналитику) → чек-ин на следующий день → еженедельный взгляд сверху → инсайт на Home → месячный пост-анализ с корректировкой программы → (при пропаже) «готов вернуться?». Поверх петли — память о личном, цели и неформальный тон (фаза 6), которые превращают рассылку в отношения.

**Метрика этапа** (BRD §9): я сам получаю пользу от каждого касания тренера — ни одно сообщение не хочется отключить. Прокси: AI-чат ≥ 5 сообщений/нед, сводки читаются (тап на inline-кнопки), напоминание реально возвращает в зал.

## Фаза 0 — Технический фундамент (без него любая фича = копипаста)

Ничего пользовательского, 4 строительных блока. Всё остальное опирается на них.

### 0.1 `notifier` — отправка сообщений по telegramId вне update-контекста
Сейчас `bot` живёт в module scope `server/src/index.js` и не экспортируется; все отправки — `ctx.reply()`. Нужен модуль `src/bot/notifier.js`:
- `setBot(bot)` вызывается из `index.js` после `createBot()`; `notify(telegramId, html, { buttons })` → `bot.telegram.sendMessage(chatId, ...)`.
- **parse_mode: 'HTML' + escape-helper** — сразу, не Markdown: имена упражнений/программ из LLM с непарным `*`/`_` роняют Markdown-parse (известная проблема, см. CODE_REVIEW_PLAN). Постепенно перевести существующие `ctx.reply` тоже на HTML.
- Fire-and-forget семантика как у `track()`: ошибка отправки (юзер заблокировал бота) логируется, не бросает.

### 0.2 Вынести агрегации из контроллеров в `services/statsService.js`
Вся аналитика сейчас зашита в req/res-хендлеры (`statsController.js`, `progressController.js`) — переиспользовать в сводках/инсайтах можно только копипастой. Рефакторинг в чистые функции `(userId, opts) => data`:
- `computeStreak(userId)` — уже существует (statsController.js:74), просто экспортировать;
- `getMonthStats(userId)`, `getWeekStats(userId)` (тоннаж, тренировки, сравнение с прошлым периодом);
- `getRecords(userId, period)` — CTE из progressController;
- `getMuscleVolume(userId, period)`, `getPlanAdherence(userId)`;
- `getWorkoutSummary(workoutId)` — сеты по упражнениям + сравнение с прошлой тренировкой того же дня (прогресс/регресс по весам).
Контроллеры становятся тонкими обёртками. Словари `MUSCLE_GROUP_MAP`/`EXERCISE_MUSCLE_OVERRIDE` переезжают из progressController в сервис. Заодно закрывается пункт техдолга из CODE_REVIEW_PLAN.

### 0.3 `buildUserContext()` — единый контекст юзера для LLM
`services/aiTrainer/buildUserContext.js` — один сборщик, который используют чат, сводки, инсайты и пост-анализ (разными подмножествами через опции):
```
{ profile,                  // цель, опыт, ограничения, оборудование
  activeProgram,            // name, days (кратко), guidelines
  recentWorkouts,           // последние 5–10: дата, день программы, тоннаж, ключевые веса
  stats,                    // стрик, неделя/месяц, рекорды
  flags }                   // дней без тренировки, плато (фаза 4+)
```
Формат — компактный текст/markdown для system-промпта (не JSON-простыня, бережём токены). Это и есть «память тренера» — главное, что нельзя скопировать (позиционирование §4).

### 0.4 Шедулер `src/scheduler/index.js`
- `node-cron` уже в dependencies (^3.0.3), не используется — подключить в `index.js` рядом с ботом (архитектура «один процесс» сохраняется, см. ARCHITECTURE).
- Тик раз в час; для каждого юзера вычисляем локальное время через `User.timezone` (поле есть, **не заполняется** — начать писать из `ctx.from`/initData при auth, fallback `Europe/Moscow`).
- **Идемпотентность обязательна** (Railway рестартует процесс): модель `NotificationLog { userId, kind, periodKey, sentAt, @@unique([userId, kind, periodKey]) }` — перед отправкой `create` в try/catch, дубль = пропуск. `periodKey` = `2026-W24`, `2026-06` и т.п.
- Настройки: `UserProfile.notificationsJson Json?` (nullable — безопасно через `db push`): `{ postWorkout: true, weekly: true, monthly: true, reminders: true, records: true }`. UI-переключатели — позже на экране `/me`; пока дефолт «всё включено».

**Definition of done фазы:** `notify()` шлёт мне сообщение из node-REPL/скрипта; `getWeekStats(userId)` вызывается из скрипта без Express; cron-тик пишет NotificationLog без дублей при рестарте.

## Фаза 1 — Пост-тренировочная сводка ⭐ (сценарий 2.4)

**Ценность:** самое частое касание тренера — после каждой тренировки. Чинит сломанное обещание Summary-экрана. Это «поддерживает после тренировки» в чистом виде.

**Поток:** finish-хук в `workoutController.update()` (рядом с `track('workout_completed')`, стр. ~352 — данные уже есть: `req.user` с telegramId, workout со всеми sets+exercise) → fire-and-forget `sendPostWorkoutSummary(user, workout)`:
1. `getWorkoutSummary()` + `getMonthStats()` + `getPlanAdherence()` из statsService — **числа считаем кодом, не LLM** (LLM врёт в арифметике);
2. один `llm.chat()` с компактным контекстом → 2–4 предложения «наблюдения тренера» (тон: поддержка без сюсюканья, конкретика: «жим +2.5 кг — отлично, в следующий раз пробуй 75×8»);
3. сообщение: цифры (код) + наблюдение (LLM) + inline-кнопки `[📊 Детали]` (deep-link `progress`) `[💬 Обсудить]`;
4. при фейле LLM — деградация до чисто числовой сводки (паттерн fallback уже принят в aiTrainer-сервисах).

**Новое:** `services/aiTrainer/postWorkoutSummary.js`, промпт `prompts/postWorkoutSummary.md`. Рекорд-детект: если `getRecords` видит новый PR — отдельная строка «🏆 Новый рекорд» в этом же сообщении (не отдельный пуш, не спамим).

**Edge cases (из USER_SCENARIOS 2.4):** не все подходы → «4 из 6, продолжим в следующий раз»; первая тренировка → поздравление; тренировка удалена (0 сетов) → ничего не шлём.

**Стоимость:** ~1 LLM-вызов на тренировку (sonnet, maxTokens 512) — копейки.

## Фаза 2 — AI-чат с контекстом (сценарий 2.6)

**Ценность:** «коммуницирует и даёт советы в каждой сессии» — ядро тренера. Без него все сводки — монолог.

### 2.1 Базовый чат в боте

**Реализация — в боте** (по дихотомии USER_SCENARIOS §1: бот = диалог), мини-апп не трогаем:
- `bot.on('text')` fallback-хендлер (после команд и сцен; в сценах guard `ctx.scene?.current` — пропускать);
- `services/aiTrainer/chat.js`: история = последние ~20 ChatMessage из БД + `buildUserContext()` в system → `llm.chat()` → сохранить оба сообщения в ChatMessage (модель готова, поля role/content/model/tokens — заполнять usage из ответа llm);
- system-промпт `prompts/chatTrainer.md`: роль тренера, рамки (только тренировки/фитнес — мягкий возврат в тему), **медицинский дисклеймер** (симптомы → «к врачу», без советов — риск из BRD §10), язык ru;
- `sendChatAction('typing')` пока ждём LLM;
- роут `/api/v1/chat` (TODO в routes/index.js:18) — **не делаем**: чат живёт в Telegram, это и есть нативный UI.

**Контекст активной тренировки:** если есть незавершённый Workout — добавить в контекст («сейчас тренировка: День 2, сделано 3/6 упражнений, последний сет жим 60×10»). Это даёт сценарий «поясница тянет на приседе» с осмысленным ответом.

### 2.2 Контекстные входы: чат про программу и конкретное упражнение

Юзер не должен объяснять тренеру, о чём речь — контекст передаёт мини-апп:

- **Точки входа в мини-аппе:** «Спросить тренера» на WorkoutPage (quick action из BRD §12.2), кнопка в ExerciseDetailSheet («Спросить про упражнение»), «Обсудить программу» на ProgramEditPage.
- **Механика handoff:** `Telegram.WebApp.sendData` **не подходит** — работает только для апп, открытых с keyboard button (наш открывается через Menu Button / inline). Вместо этого: `POST /api/v1/chat/context { type: 'exercise'|'program'|'workout', refId }` → запись в модель `PendingChatContext { userId, type, refId, payload Json, createdAt }` (TTL ~10 мин) → `Telegram.WebApp.openTelegramLink(t.me/bot)`. Бот при следующем сообщении (или сразу проактивно через notifier: «Ты про жим лёжа — спрашивай!») подхватывает контекст и кладёт его в system.
- **Контекст по типам:**
  - *exercise* — данные Exercise (техника, мышцы, typicalMistakes) + история юзера по нему (последние сеты, тренд веса, плато-статус из фазы 4);
  - *program* — `planJson` (компактно: дни + упражнения) + `guidelines` + adherence. Сценарии: «зачем мне 5 подходов на грудь в день 1?», «можно поменять день 2 и 3 местами?»;
  - *workout* — активная тренировка (уже в 2.1).

### 2.3 Аналитика по запросу (tool use)

«Как у меня прогресс по жиму?», «сколько тоннажа за месяц?», «что у меня отстаёт?» — LLM не угадывает, а **дёргает функции**:

- Расширить `llm.js`: `chat(messages, { tools, executeTool })` — agentic-петля (response `tool_use` → выполнить → `tool_result` → продолжить, лимит ~3 раунда). Это пригодится и фазе 5 (действия из чата).
- Набор инструментов — тонкие обёртки над `statsService` (фаза 0): `get_exercise_history(slug, period)`, `get_period_stats(week|month)`, `get_records(period)`, `get_muscle_volume(period)`, `get_program_details()`, позже `get_plateaus()` (фаза 4).
- Числа форматирует код (принцип №1), LLM интерпретирует: «Жим: 67.5→75 за месяц, +11%. Темп хороший, не торопись с +5 кг скачками».
- Деградация: если tool-петля упала — отвечаем из базового контекста buildUserContext (там уже есть свод).

**Пока без** function-calling-**действий** («замени упражнение в программе» из чата) — это фаза 5; сначала тренер читает данные, потом меняет их.

**Лимиты:** maxTokens 1024, обрезка истории, лимит tool-раундов, на этапе «для себя» rate limit не критичен (но не забыть перед открытием друзьям — см. CODE_REVIEW_PLAN Фаза 0).

## Фаза 3 — Проактивность: weekly-сводка + напоминания (сценарии 3.2 + retention)

**Ценность:** «следит за прогрессом» между тренировками. Первый потребитель шедулера.

### 3.1 Еженедельная сводка (вс, вечер по timezone юзера)
- cron-тик → юзеры с `localTime ∈ [19:00, 20:00)` и воскресенье → `NotificationLog(kind='weekly', periodKey='2026-W24')`;
- состав: `getWeekStats` + `getRecords(week)` + `getPlanAdherence` (код) + 1 LLM-наблюдение (промпт `prompts/weeklySummary.md`);
- тон из USER_SCENARIOS 3.2: план — ориентир, не KPI. Пропустил неделю → «всё ок, жизнь» (без вины); перевыполнил → про восстановление;
- inline: `[📊 Отчёт]` `[▶️ Начать следующую]` (deep-links — зависимость: парсер `src/utils/deepLink.js` из Фазы 6 implementation-plan; до него кнопки ведут просто в мини-апп).

### 3.2 Напоминание «Готов вернуться?» (7+ дней тишины)
- ежедневный тик: `MAX(finishedAt) < now - 7d` и нет активной тренировки → одно ободряющее сообщение, **без LLM** (3–4 заготовки, ротация);
- анти-спам: не чаще 1 раза в 10 дней (`NotificationLog`), после 3 неотвеченных — замолкаем до возвращения юзера (уважение > retention-давилка).

### 3.3 Условие отправки сводок
Юзеры с ≥ 1 тренировкой за период; новым без программы не шлём ничего.

## Фаза 4 — Инсайты: плато/дисбалансы + «замечание тренера» на Home

**Ценность:** тренер «замечает» — то, чего нет ни у одного трекера. Закрывает 🔜 из PRODUCT_PLAN §6 и AI-инсайт из BRD §12.1.

### 4.1 Детекция (код, не LLM) — `services/insightsService.js`
- **Плато:** по упражнению N последних тренировок без роста веса/повторов (SQL поверх WorkoutSet, паттерн raw-CTE уже есть в records);
- **Дисбалансы:** соотношения из muscleVolume (грудь vs спина, передние vs задние дельты — пороги захардкодить);
- **Регрессия:** падение рабочего веса 2+ тренировки подряд.
Выход — структурированные факты `{ type, exercise/muscles, severity, data }`.

### 4.2 Подача
- **Progress-экран:** чипы «⚡ N в плато / 📈 растёт / ↩️ просели» + карточки (UI по BRD §12.4) — `GET /api/v1/progress/insights`, без LLM;
- **AI-инсайт на Home** (`GET /api/v1/insights/today`): раз в день LLM упаковывает топ-1 факт в «замечание тренера» (2–3 предложения + CTA), кэш в новой модели `Insight { userId, date, payload Json, @@unique([userId, date]) }`; генерация лениво при первом запросе дня (не cron — юзер может не зайти);
- **Интеграция в сводки:** факты из insightsService попадают в контекст weekly/monthly промптов — сводки становятся зрячими.

## Фаза 5 — Ежемесячный пост-анализ с действиями (сценарий 3.3)

**Ценность:** замыкает петлю «следит → советует → **меняет программу**». Самая «тренерская» фича: план vs факт + предложение корректировки.

- Cron: каждые 4 недели от активации программы (хранить отсчёт от `Program.updatedAt`/активации; periodKey = номер месяца на программе);
- Анализ: факт частоты vs план, распределение по дням программы (A/B-перекос — `programDayIndex` есть на Workout), прогресс тоннажа, инсайты из фазы 4 → LLM-разбор (промпт `prompts/monthlyReview.md`);
- **Кнопки-действия:** `[Сохранить как есть]` `[Сократить до N/нед]` `[Сбалансировать]` `[Новая программа]` — callback-хендлеры в боте:
  - «Сократить/Сбалансировать» — LLM-модификация `planJson` существующей программы (вход: текущий planJson + указание; переиспользовать zod-схемы и resolveExercise из importProgram);
  - «Новая программа» → `ctx.scene.enter('generate-program')` (сцена есть);
- Молчание юзера = ничего не меняем (повтор через 4 недели).

Сюда же мелочь из бэклога: **настраиваемая годовая цель** — `UserProfile.annualTarget Int?` вместо env `ANNUAL_WORKOUT_TARGET`, спрашивается в чате/визарде, редактируется на `/me` (позже поглощается моделью Goal, см. 6.2).

## Фаза 6 — Человечность: тренер, а не бот

То, из-за чего возникает «меня ведёт человек», а не «мне шлёт отчёты скрипт». Не монолитная фаза: 6.5 (тон) применяется с первого промпта фазы 1, 6.3 частично едет со сводками, полные 6.1/6.2/6.4 требуют чата (фаза 2).

### 6.1 Память о личном (TrainerNote)
Бот помнит сеты — тренер помнит *тебя*: «как плечо, не беспокоит после прошлого раза?»

- Модель `TrainerNote { userId, kind (injury|complaint|preference|life_context), content, status (active|resolved), createdAt }`.
- Извлечение: после чат-диалога и при `Workout.notes`/низком feltRating — fire-and-forget LLM-вызов (промпт `prompts/extractNotes.md`): новые факты → create, отработанные → resolved.
- `buildUserContext()` получает блок «Заметки тренера» (только active, лимит ~10); промпты чата и сводок инструктируются **возвращаться к темам** («в прошлый раз жаловался на поясницу — как сейчас?»).
- Контроль: «забудь про X» в чате → resolve; заметки видны юзеру по запросу («что ты обо мне помнишь?»).

### 6.2 Цели и вехи
Закрывает «помогает ставить цели» из исходного видения.

- Модель `Goal { userId, type (exercise_weight|frequency|annual|custom), exerciseId?, targetValue, deadline?, status, achievedAt? }`.
- Постановка — в диалоге: тренер сам предлагает после 2–3 недель данных («жмёшь 80 — хочешь к осени сотку?»), юзер может попросить любую. Tool `create_goal` — первое **пишущее** действие чата (безопасное, с подтверждением кнопкой).
- Прогресс к целям — в `buildUserContext` и сводках: «до сотки осталось 7.5 кг, идёшь с опережением графика».
- Достижение: детект на finish-хуке → праздничное сообщение + предложение следующей цели. `UserProfile.annualTarget` из фазы 5 мигрирует в `Goal(type=annual)`.

### 6.3 Реакции в моменте
Тренер реагирует на происходящее, а не только по расписанию:

- **PR прямо во время тренировки:** хук в `logSet` — сравнение с историческим максимумом (дёшево, по индексу) → мгновенное короткое сообщение в бот (вариативные заготовки, без LLM). Анти-спам: максимум 1 реакция за тренировку, не дублируется в пост-сводке.
- **Низкий feltRating (1–2):** пост-сводка меняет тон — не «отличная работа», а «вижу, тяжело зашло — что было не так?» (ответ → чат → TrainerNote).
- **Возвращение после паузы 7+ дней:** пост-сводка начинается с «с возвращением» (не нравоучений).
- **Анти-шаблонность:** в контекст промптов сводок передаются 2–3 последних отправленных сообщения тренера с инструкцией «не повторяй формулировки». Одинаковое «Отличная тренировка! 💪» три раза подряд — главный признак бота.

### 6.4 Чек-ины: тренер спрашивает
- Шедулер: на следующий день после тяжёлой тренировки (тоннаж выше ~80-го перцентиля юзера или feltRating ≤ 2) — «как восстановление, мышцы как?». Ответ уходит в чат-петлю → extractNotes (кормит 6.1).
- Weekly-сводка заканчивается вопросом, а не только кнопкой («что на неделе далось тяжелее всего?»).
- Анти-спам: чек-ин — проактивное сообщение (общий лимит 1/день), не чаще 2 раз в неделю, отключаем для молчащих (3 чек-ина без ответа → пауза).

### 6.5 Неформальный тон — «друг-тренер»
- Общий фрагмент `prompts/_tone.md`, включается во **все** промпты (сводки, чат, чек-ины, инсайты): разговорный русский, на «ты», по имени, короткие сообщения как в мессенджере (1–3 абзаца), юмор и эмодзи точечно, без канцелярита и коуч-пафоса, иногда встречный вопрос вместо утверждения.
- Small talk не обрывается: на оффтоп чат отвечает по-человечески коротко и мягко возвращает к делу (edge case из USER_SCENARIOS 2.6).
- Выбор персоны тренера (угрюмый качок / фитоняшка / норм паренёк) — за горизонтом, PRODUCT_PLAN §7; `_tone.md` — будущая точка подмены персоны.

Фаза 0 (фундамент)

**Связь с CODE_REVIEW_PLAN.md:** перед фазой 2 желательно закрыть оттуда Фазу 0 (безопасность — чат расширяет поверхность LLM-абьюза) и пункт «in-memory session бота» становится актуальнее с ростом диалогов.

## Сквозные принципы

1. **Числа — кодом, слова — LLM.** Все цифры в сообщениях считает statsService; LLM только интерпретирует. Никакой арифметики в промптах.
2. **Деградация без LLM.** Любая сводка/инсайт при фейле LLM отправляется в чисто числовом виде (паттерн `{success, error}` из aiTrainer уже задан).
3. **Тон тренера** — единый фрагмент `prompts/_tone.md` в каждом промпте (детали в 6.5): неформальный «друг-тренер», поддержка без сюсюканья, конкретика с числами, план — ориентир, а не KPI, никакой вины за пропуски, медицина → к врачу. Это прямые требования USER_SCENARIOS 3.2 и BRD §10.
4. **Анти-спам.** Максимум 1 проактивное сообщение в день; рекорды встраиваются в сводки, а не шлются отдельно; NotificationLog — единая защита от дублей.
5. **Все промпты — `.md` в `services/aiTrainer/prompts/`** (правило проекта), все вызовы через `llm.js`, вся отправка через `notifier`, вся аналитика касаний через `track()` (`summary_sent`, `chat_message`, `insight_shown`, `reminder_sent`, `monthly_action_chosen`).
6. **Нулевые миграции-риски:** все новые поля nullable / новые модели — безопасный `db push` (правила schema.prisma соблюдаем).
