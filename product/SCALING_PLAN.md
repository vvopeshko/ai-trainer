# SCALING_PLAN — развитие архитектуры до запуска

План эволюции архитектуры под рост: **Фаза 1 — до 100 активных пользователей** (близкий круг + мягкий запуск), **Фаза 2 — до 1000 активных** (коммерческий запуск).

**Создан:** 2026-06-12. Текущая архитектура — [ARCHITECTURE.md](ARCHITECTURE.md), известные проблемы кода — [CODE_REVIEW_PLAN.md](CODE_REVIEW_PLAN.md), AI-слой — [AI_TRAINER_PLAN.md](AI_TRAINER_PLAN.md).

---

## 0. Главный тезис: узкое место — не нагрузка

Реалистичная оценка трафика:

| | 100 MAU | 1000 MAU |
|---|---|---|
| DAU (~25%) | ~25 | ~250 |
| Пик одновременных (вечер в зале) | ~5–8 | ~40–60 |
| API RPS в пике (лог подходов и чтения) | < 1 | ~5–10 |
| LLM-вызовов/день (чат + сводки + сканы) | ~50–150 | ~1500–4000 |
| Строк WorkoutSet/мес | ~10–20K | ~150–300K |

Один Node-процесс на Railway и Neon справляются с этим **с огромным запасом** — по чистому CPU/IO текущий монолит выдержит и 1000 пользователей. Реальные риски в другом, и фазы построены вокруг них:

1. **Стоимость и абьюз LLM** — единственный ресурс, который масштабируется линейно с юзерами и стоит денег.
2. **Надёжность одного процесса** — деплой роняет бота на минуту, in-memory сессии теряются, cron и API делят один event loop.
3. **Операционная слепота** — нет error tracking, алертов, дашборда стоимости; о проблеме узнаём от юзера.
4. **Безопасность данных** — `db push` без миграций, дев и прод на одной БД, IDOR-риски.

Принцип из ARCHITECTURE.md сохраняем: **не добавлять инструмент, пока не заболело**. Для каждого изменения ниже указан триггер «когда пора».

## Фаза 1 — до 100 активных (близкий круг → мягкий запуск)

Цель фазы: **чужие люди могут пользоваться продуктом, не ломая его и не разоряя автора**. Архитектурно почти ничего не меняем — наводим операционный порядок.

### 1.1 Безопасность — блокеры запуска

- ✅ ~~Auth hardening~~ — auth_date expiry, fail-closed dev_bypass, rate limiting (global 100/min + LLM 5/min), body limit 1MB — **сделано** (см. ARCHITECTURE §5.1).
- [ ] **Дозакрыть Фазу 0–1 из CODE_REVIEW_PLAN:** IDOR на чужую программу (`workoutController`), partial unique index на активную тренировку, generic-ошибки при 500.
- [ ] **Лимиты на все LLM-эндпоинты,** включая новые из AI_TRAINER_PLAN (чат в боте — лимит на стороне бот-хендлера: N сообщений/час на юзера, мягкий отказ «дай мне минуту»).
- [ ] **Kill switches:** env-флаги `FEATURE_CHAT`, `FEATURE_SCAN`, `FEATURE_SUMMARIES` — возможность мгновенно выключить дорогую/сломанную фичу без деплоя (Railway env update = рестарт, приемлемо).

### 1.2 Контроль стоимости LLM

При 100 юзерах LLM — главная статья расходов (~$10–40/мес при разумных лимитах, но абьюз может сделать любые цифры).

- [ ] **Учёт токенов повсеместно:** `ChatMessage.tokensInput/Output` уже есть — писать их во всех вызовах; для не-чатовых (сводки, сканы) — `track('llm_call', { feature, tokens, model })` в AnalyticsEvent.
- [ ] **Дневной бюджет на юзера:** простая проверка перед LLM-вызовом (`SUM(tokens) за сегодня > N` → вежливый отказ). Без новых таблиц — запрос к AnalyticsEvent/ChatMessage.
- [ ] **Дешёвая модель для рутины:** сводки/чек-ины/извлечение заметок — Haiku-класс; Sonnet — только чат, генерация программ и vision. Точка смены — `options.model` в `llm.js`, уже поддерживается.
- [ ] **Prompt caching** Anthropic для system-промптов и `buildUserContext` (повторяющийся префикс в чате) — минус 50–90% на input-токенах самой частой операции. Требует обновить `@anthropic-ai/sdk` (сейчас ^0.33, известный пункт из ревью).
- [ ] **Админ-дашборд расходов:** `/api/v1/analytics/llm?key=ANALYTICS_SECRET` — токены/стоимость по дням, фичам, юзерам. Смотреть раз в неделю.

### 1.3 Наблюдаемость — минимальный набор

- [ ] **Sentry** (фронт + бэк, free tier): сейчас ошибки фронта молча глотаются (известно из ревью), ошибки бэка живут только в Railway-логах. Подключение — час работы, окупается первым же инцидентом.
- [ ] **Uptime-мониторинг:** внешний пинг `GET /api/health` (UptimeRobot/BetterStack free) + алерт в Telegram. Бонус: проверка «бот жив» — `getMe()` в health-ответе.
- [ ] **Структурные логи** для LLM-вызовов и шедулера (JSON-строки: feature, userId, duration, tokens, error) — хватит Railway-логов, без отдельного стека.

### 1.4 Операционный порядок

- [ ] **Разделить dev и prod БД.** Сейчас локальная разработка ходит в ту же Neon-базу, что прод (ARCHITECTURE §8) — при чужих данных это недопустимо (один `seed:dev` или кривой `db push` с локалки бьёт по живым юзерам). Решение бесплатное и нативное: **Neon branch** `dev` от прод-базы; `server/.env` локально указывает на branch. Прод-`db push` — только осознанно, с зафиксированным timestamp (правило уже есть).
- [ ] **Починить Railway автодеплой** (известный баг «GitHub Repo not found» из NEXT_PLANS) — ручной деплой при запуске на людей опасен «забыл задеплоить фикс».
- [ ] **GitHub Actions CI:** `build + lint + test:all` на PR/push. Pre-push хук остаётся, но CI — страховка от `--no-verify` и основа для будущих контрибьюторов. ~30 строк yaml.
- [ ] **Сессии бота → PostgreSQL.** In-memory `session()` теряет состояние WizardScene на каждом деплое (юзер посреди анкеты «зависает» — для близкого круга простительно, для 100 незнакомых это сломанный онбординг). Готовый адаптер `@telegraf/session` + таблица или своя `BotSession { key, data Json }` — Redis для этого **не нужен**.
- [ ] **Graceful shutdown:** `prisma.$disconnect()` + таймаут на `server.close()` (из CODE_REVIEW_PLAN) — при деплоях посреди LLM-вызовов.
- [ ] **Активационная воронка:** admin-эндпоинты `/analytics/funnel` (события уже пишутся) — без этого не видно, где отваливаются первые юзеры. Это метрика этапа «близкий круг» из BRD §9.

### 1.5 Что НЕ делаем в фазе 1 (осознанно)

Webhook для бота (long polling ок), Redis, очереди, горизонтальное масштабирование, выделенный worker, TypeScript-миграция, Kubernetes/Docker, микросервисы, CDN для медиа, прогрев кэшей. Всё это — решения проблем, которых при 100 юзерах нет.

**Definition of done фазы 1:** незнакомый человек проходит онбординг без моей помощи; я узнаю́ об ошибке из Sentry раньше, чем из чата; вижу недельный расход LLM в одном запросе; деплой не ломает ничьё состояние; локальная разработка не может тронуть прод-данные.

## Фаза 2 — до 1000 активных (коммерческий запуск)

Цель фазы: **продукт переживает деплои незаметно для юзеров, расходы предсказуемы и покрываются подпиской, данные защищены процессом, а не дисциплиной**.

### 2.1 Надёжность процесса: монолит → «монолит + worker»

Микросервисы не нужны, но один процесс на всё (API + бот + cron + LLM-вызовы) к 1000 юзерам создаёт две реальные проблемы: деплой = минута даунтайма бота, и волна еженедельных сводок (сотни LLM-вызовов) конкурирует с живым трафиком.

- [ ] **Бот: long polling → webhook.** Тот же Express-процесс, роут `POST /telegram/webhook/<secret>` (`bot.webhookCallback`). Зачем: мгновенный рестарт без «отлипания» от polling, нет конфликта двух инстансов при деплое (Railway поднимает новый до остановки старого — с polling это даёт `409 Conflict`), готовность к нескольким репликам.
- [ ] **Выделить worker-процесс** (второй Railway-сервис из той же кодовой базы, `npm run worker`): шедулер + рассылки сводок + тяжёлые LLM-джобы. API-процесс остаётся отзывчивым; worker можно ронять/рестартовать безболезненно. Идемпотентность уже обеспечена `NotificationLog` (AI_TRAINER_PLAN фаза 0).
- [ ] **Очередь LLM-джобов в Postgres,** не Redis: таблица `Job { id, kind, payload, status, runAt, attempts }` + воркер с `SELECT ... FOR UPDATE SKIP LOCKED` (или готовый `pg-boss`). Сглаживает волну воскресных сводок (1000 юзеров × LLM = растянуть на час, уважая rate limits Anthropic), даёт ретраи. **Redis вводим только если** появится вторая реплика API с общим rate limiting — до тех пор Postgres хватает на всё.
- [ ] **Батчи для рассылок:** weekly/monthly сводки через Anthropic **Batch API** (−50% стоимости, результат в течение часа — для воскресной сводки идеально).

### 2.2 База данных

- [ ] **Connection pooling:** перейти на pooled connection string Neon (PgBouncer) для API-процесса — два процесса × Prisma pool легко упираются в лимит соединений Neon. Прямое соединение оставить только для `db push`.
- [ ] **Перейти с `db push` на `prisma migrate`.** При 1000 платящих юзеров «правила дисциплины» — недостаточная защита (история daily balancer это уже доказала). Миграции дают: ревью SQL до применения, воспроизводимость dev→prod, откат. Переход: `prisma migrate diff` от текущей схемы → baseline. Правила из §5.2 ARCHITECTURE остаются для экстренного ручного SQL.
- [ ] **Индексы под рост** (из CODE_REVIEW_PLAN): `Workout(userId, finishedAt)`, `Workout(programId)`, GIN на `Exercise.aliases`; партицирование/rollup `AnalyticsEvent` (к 1000 MAU это миллионы строк/год: сырые события старше 90 дней → агрегаты + удаление, cron-джоб в worker).
- [ ] **Neon autoscaling:** поднять max compute units; PITR-окно расширить (платный план) — стоимость копеечная относительно рисков.

### 2.3 Данные и медиа

- [ ] **R2 наконец реализовать** для фото тренажёров (сейчас — Telegram file_id, doc/code mismatch из ревью): фичу открываем всем (сейчас admin-only), фото нужны для итерации промпта и датасета.
- [ ] **GIF-ки упражнений → своё хранилище.** Сейчас hotlinking на ExerciseDB OSS: при 1000 юзеров это (а) хрупко — чужой сервис без SLA в критичном UI, (б) сомнительно по AGPL-условиям при коммерческом использовании. Перелить в R2 (+CDN из коробки), проверить лицензионную чистоту, при необходимости заменить источник.
- [ ] **GDPR-механика:** экспорт данных юзера (JSON-дамп по userId) и полное удаление (`onDelete: Cascade` уже выстроен — нужен только эндпоинт + команда в боте). Обязательное условие приёма платежей в ЕС/UK-юрисдикциях.

### 2.4 Стоимость LLM как часть юнит-экономики

- [ ] **Квоты по тарифам:** бюджеты из фазы 1 привязываются к подписке (free trial: N сообщений чата + 1 генерация; paid: щедрые лимиты). Техника готова (учёт токенов), добавляется проверка тарифа.
- [ ] **Кэш повторяющихся ответов:** одинаковые вопросы новичков («как делать жим?») и повторные сканы того же тренажёра — кэш по нормализованному ключу в Postgres. Включать по данным из дашборда (если топ-10 вопросов дают >20% вызовов).
- [ ] **Целевая метрика:** LLM-себестоимость на активного юзера < 15–20% ARPU (при $9.99/мес — бюджет ~$1.5–2/юзер/мес, это ~цена 100–200 сообщений Sonnet с prompt caching — достаточно).

### 2.5 Наблюдаемость и процессы

- [ ] **Алерты, а не дашборды:** error rate spike (Sentry), health down (UptimeRobot), дневной LLM-расход > порога (cron-джоб в worker → сообщение админу в Telegram), очередь джобов растёт.
- [ ] **Staging-окружение:** Railway preview environment + Neon branch на PR — проверка миграций и фич на копии прод-данных до деплоя.
- [ ] **Интеграционные тесты API** против Neon branch в CI (ревью отметило: вся бизнес-логика контроллеров не покрыта; к коммерческому запуску — must).
- [ ] **TypeScript для `services/aiTrainer/`** — по Decision Log §7 «когда заметная AI-логика с JSON-схемами»: к фазе 2 она заметная (чат, tools, сводки, заметки). Только сервисный слой, не переписывание всего.

### 2.6 Что НЕ делаем и в фазе 2

Kubernetes, микросервисы, Kafka/RabbitMQ, собственная инфраструктура, мульти-регион, GraphQL, переписывание фронта. Следующий горизонт (10K+) — отдельный план, когда (если) понадобится.

**Definition of done фазы 2:** деплой незаметен для юзера (webhook + worker); воскресная рассылка 1000 сводок не влияет на API и стоит вдвое дешевле (batch); схема БД меняется через ревьюируемые миграции; расход LLM на юзера известен и заложен в цену подписки; инцидент приходит алертом до жалобы юзера.

## Сводная карта переходов

| Компонент | Сейчас (≈1 юзер) | Фаза 1 (100) | Фаза 2 (1000) |
|---|---|---|---|
| Процессы | 1 (API+бот+cron) | 1, без изменений | 2: API+бот / worker+cron |
| Бот ↔ Telegram | long polling | long polling | **webhook** |
| Сессии бота | in-memory | **PostgreSQL** | PostgreSQL |
| Очереди | — | — (cron + NotificationLog) | **Postgres-очередь (pg-boss)** |
| Схема БД | `db push` | `db push` + dev-branch | **`prisma migrate`** |
| Соединения БД | прямые | прямые | **PgBouncer (pooled)** |
| Dev-данные | общая БД с прод | **Neon branch** | Neon branch + staging |
| LLM-стоимость | не учитывается | **учёт + бюджеты + prompt caching + Haiku для рутины** | квоты по тарифам + Batch API + кэш ответов |
| Ошибки | Railway-логи | **Sentry + uptime-пинг** | + алерты (LLM-расход, очередь) |
| CI | pre-push хук | **GitHub Actions** | + интеграционные тесты, staging |
| Медиа | hotlink ExerciseDB | hotlink | **R2 + лицензионная проверка** |
| Redis | — | — | только при 2+ репликах API |

## Триггеры «пора переходить»

- Жалоба «бот завис посреди анкеты» после деплоя → сессии в Postgres (если ещё не).
- `409 Conflict` от Telegram при деплое или даунтайм бота заметен юзерам → webhook.
- Воскресная рассылка занимает > 10–15 мин или душит API → worker + очередь.
- Лимит соединений Neon в логах → PgBouncer.
- LLM-расход за месяц превысил план ×1.5 → квоты ужесточить, кэш включить.
- Любой инцидент с данными или страх перед `db push` → ускорить переход на migrate (не ждать фазу 2).
